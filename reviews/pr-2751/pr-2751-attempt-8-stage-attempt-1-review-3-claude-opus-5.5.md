## Issues

### Issue 1: Malformed `OMP_NUM_THREADS` tail skips the affinity fallback
- **Severity**: Low
- **File**: `lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/LightGBMUtils.scala`
- **Line(s)**: 127-132, 222-230
- **Description**: `firstOmpTeamSize` reads the first comma token and ignores the rest of the list. OpenMP runtimes validate the whole list. GNU libgomp and LLVM/Intel libomp both reject `8,abc` and `8,-1`. libgomp also rejects `8,` and `8,0`, and LLVM rejects a leading `+`. A runtime that rejects the list prints a warning and makes the CPU count of the process affinity mask the default team. SynapseML still returns 8, so `streamingOmpAllocationBound` never reaches the affinity fallback at line 223. Example: a Linux executor has 32 CPUs in its affinity mask, `OMP_NUM_THREADS=8,abc`, the default hint of 16, `numThreads` below 16 and no larger registered history. The bound is 16, but a fresh pooled task thread pushes with a 32-thread team. With two or more local writers, thread numbers 16 to 31 land in the next writer's slots or past the last slot. That is the `SparseBin::Push` out-of-range class this PR mitigates. The docs say the team is derived from `OMP_NUM_THREADS` (`docs/Explore Algorithms/LightGBM/Overview.md` lines 174-176, `lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/params/LightGBMParams.scala` lines 172-173), which does not hold for these values. The tests in `lightgbm/src/test/scala/com/microsoft/azure/synapse/ml/lightgbm/split1/StreamingLayoutSuite.scala` lines 114-115 and 124-126 cover only `32,8`, `invalid,64`, `32,8,4`, `0,32` and `invalid,32`. For those values Scala and the runtimes agree.
- **Risk**: Native memory corruption or a crash during streaming ingestion. It needs three things: a malformed value that the runtime warns about at startup, an affinity mask wider than every other bound input, and at least two local writers. This is not a regression, because the base bound `max(hint, numThreads)` is also too small here. It is a gap in the new derivation, and the setting is unusual, hence Low.
- **Suggested Fix**: Accept the value only when every comma element is a trimmed, unsigned, positive decimal integer, which matches the strictest runtime. Otherwise return `None` so the affinity fallback runs. A simpler option is `max(first token, affinity)` whenever the list does not fully parse. Add `StreamingLayoutSuite` cases for `8,`, `8,abc`, `8,0`, `8,-1` and `+8`.

### Issue 2: Java 8 core-dump flag is a no-op on Linux
- **Severity**: Low
- **File**: `lightgbm/src/test/scala/com/microsoft/azure/synapse/ml/lightgbm/split1/StreamingOmpRegressionSuite.scala`
- **Line(s)**: 38-48
- **Description**: On Java 8 the test passes `-XX:-CreateMinidumpOnCrash` to the child JVM to disable core dumps. In JDK 8 HotSpot only the Windows minidump code reads that flag. On Linux the fatal-error path reports the `RLIMIT_CORE` status and then calls `::abort()`, so the kernel's normal core handling still applies. The cross-platform `CreateCoredumpOnCrash` switch arrived in JDK 9 with JDK-8074354. The supplied CI history shows 8u504 rejects that option, so the CI JDK lacks the change. The test runs only on Linux (32-33), and the supplied CI JDK is Temurin 8u504. So CI always takes the Java 8 branch, where the flag does nothing. HotSpot accepts the flag, so the test passes. But the supplied claim that the child disables core dumps does not hold on that path.
- **Risk**: Test-only, with no product impact. Suppose the regression returns on a Java 8 Linux agent with a nonzero core limit. The child, with a 2 GiB heap plus native memory, can then write a large core. A relative `core_pattern` puts it in the temp directory, which `finally` deletes (73-75). An absolute or piped pattern, such as systemd-coredump or apport, puts it outside the confined directory. Writing the core can also delay the failure. Credential exposure stays low because the child environment is cleared (50).
- **Suggested Fix**: On Linux, start the child as `/bin/sh -c 'ulimit -c 0 && exec "$@"' sh <java> <args...>`. Use the absolute `/bin/sh` path because `PATH` is cleared. `exec` keeps the same PID, so the timeout's forced destroy still reaches the JVM. With a zero limit the kernel skips file cores, and common pipe handlers such as systemd-coredump honor the limit. Keep `-XX:-CreateCoredumpOnCrash` for Java 9 and later. If a shell wrapper is unwanted, rename the value, add a comment that Java 8 relies on the agent's core limit, and correct the evidence wording.

## Not counted as issues
- Unverified concern, `OMP_DYNAMIC`: one writer now gets -1 (`lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/LightGBMUtils.scala` lines 218-220), so LightGBM sizes the slots from one team measurement in `LGBM_DatasetInitStreaming`. The base code returned `max(hint, numThreads)` whenever both were positive. That was the usual case, because the execution default for `numThreads` is tasks per executor minus one (`lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/LightGBMBase.scala` lines 440-442). With static teams, -1 is exact, because the same thread initializes and pushes with no thread-count-changing native call in between (`lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/StreamingPartitionTask.scala` lines 117-128). With `OMP_DYNAMIC=true`, libgomp sizes each team from current load, so the init-time team can be smaller than a later push team. I did not count this. LightGBM's own SparseBin also sizes push buffers from one team measurement and indexes by thread number, so dynamic teams fall outside the native library's safe envelope in general. I did not reproduce it. A doc note, or the positive multi-writer bound when `OMP_DYNAMIC` is truthy, would close it cheaply.
- Documented limits: native code outside SynapseML, a concurrent fit that raises a pooled thread's team after allocation, affinity that differs from a team's width after thread binding, and the best-effort processor-count fallback on non-Linux hosts or when `/proc` is unreadable (`docs/Explore Algorithms/LightGBM/Overview.md` lines 182-191). These match the PR's stated scope.
- Documented tradeoff: the high-water mark lasts for the JVM's lifetime and never falls, and the 16-slot floor costs memory (`docs/Explore Algorithms/LightGBM/Overview.md` lines 177-179 and 193-197). The supplied header arithmetic gives about 3 MiB at width 16 and 12 MiB at width 64 for 2048 groups and 4 writers, before payload. On Linux the default team follows the affinity mask. So when executors share an unpinned host, width scales with host CPUs rather than executor cores. Setting `OMP_NUM_THREADS` on executors caps both the team and the width. The two supplied performance samples point in opposite directions. I did not pool them or draw a speed conclusion.
- Minor cost: the three-argument overload (`lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/dataset/ReferenceDatasetUtils.scala` lines 147-160) evaluates `osReportedProcessorCount()` eagerly. It does so even for one writer, and even when `OMP_NUM_THREADS` or affinity decides the team. On macOS that starts `sysctl` and waits without a timeout (`lightgbm/src/main/scala/com/microsoft/azure/synapse/ml/lightgbm/LightGBMUtils.scala` lines 182-207). Linux and Windows start no process. Passing the value lazily would remove the cost.
